3. SCHEMA CHANGES

3.1 New table: canonical_activities

Purpose:
- one server-controlled immutable UUID per real-world activity;
- owner-scoped source idempotency;
- canonical activity metrics and lifecycle.

Core columns:
- id uuid primary key, server-generated with gen_random_uuid();
- owner_user_id text not null;
- source_type text not null;
- source_id text not null;
- source_version text nullable;
- source_payload_hash text not null;
- source_snapshot jsonb not null;
- primary_context text not null:
  training | expedition | free_hike | mountain_simulation;
- activity_kind text not null;
- occurred_at timestamp with time zone not null;
- started_at / ended_at timestamps with time zone nullable;
- duration_seconds / distance_km nullable;
- recorded_ascent_m / validated_ascent_m / descent_m nullable;
- lifecycle text not null;
- evidence_state text not null;
- visibility text not null, default private;
- created_at / updated_at timestamps.

Constraints:
- unique(owner_user_id, source_type, source_id);
- non-negative duration, distance, recorded ascent, validated ascent, descent;
- ended_at may not precede started_at;
- explicit context, lifecycle, evidence-state, and visibility checks.

Elevation semantics:
- recorded ascent and validated ascent are separate;
- no summit altitude field;
- no simulated target elevation field;
- no credited ascent is stored on the activity itself;
- purpose-specific credited metrics belong to qualification rows.

3.2 New table: canonical_activity_evidence

Purpose:
- keep raw GPS/elevation evidence separate from activity summary data.

Properties:
- UUID primary key;
- activity and owner references;
- evidence type;
- private JSON payload;
- optional capture timestamp;
- visibility is constrained to private.

Raw GPS is never returned by GET /api/activities/:id.

3.3 New table: canonical_activity_links

Purpose:
- attach one activity to several secondary contexts without duplicating the
  activity.

Supported typed links:
- training_plan;
- training_session;
- expedition;
- expedition_stage;
- canonical_hill;
- canonical_route;
- community_route;
- challenge.

No generic completion link/type was added.
Real Summit, Expedition Completion, and Mountain Simulation remain separate
future concepts.

3.4 New table: canonical_activity_qualifications

Purpose:
- store future purpose-specific qualification outcomes instead of one global
  isVerified/isEligible boolean.

Supported purposes:
- personal_history;
- elevation_bank_personal;
- readiness;
- real_summit_evidence;
- summit_crown;
- leaderboard;
- achievement.

Each result stores status, evidence class, reason codes, rule version,
evaluation timestamp, and optional non-negative credited metric.

3.5 New table: canonical_activity_conflicts

Purpose:
- audit materially different payloads submitted for an already accepted
  owner/source identity.

It records identifiers and payload hashes, not a second raw GPS payload.
The accepted activity is not overwritten.

3.6 Existing table altered: tracked_hill_sessions

Additive change only:
- canonical_activity_id uuid nullable;
- foreign key to canonical_activities(id), ON DELETE SET NULL;
- tracked_hill_sessions_canonical_activity_idx.

Preserved:
- all existing columns and records;
- existing globally unique legacy activity_id;
- existing released-client request and response fields.

The legacy global activity_id uniqueness remains a compatibility constraint.
Canonical identity itself is correctly owner-scoped. If two owners submit the
same legacy activity ID, the canonical API can hold both owner-scoped
activities, but the tracked-hill compatibility endpoint reports HTTP 409
without returning the first owner's row.


4. API CHANGES

4.1 POST /api/activities

Authentication:
- protected by existing Clerk middleware;
- owner_user_id comes only from getAuth(req).userId;
- client-supplied owner identity is not accepted by the request schema.

Behavior:
- server generates immutable canonical UUID;
- same owner/source/payload returns the same activity with deduplicated=true;
- concurrent identical submissions create one activity;
- same source ID for different owners creates separate canonical activities;
- changed payload for the same owner/source returns HTTP 409 and records a
  conflict without overwriting the accepted activity;
- negative metrics and reversed start/end times return HTTP 400;
- visibility defaults to private;
- GPS/elevation evidence is stored in the private evidence table.

4.2 GET /api/activities/:id

Authentication/authorization:
- requires Clerk authentication;
- query is constrained by both canonical activity ID and authenticated owner;
- another owner's ID resolves as 404;
- raw evidence and source snapshot are not included in the response.

4.3 POST /api/hill-session/save-tracked compatibility bridge

Existing clients remain valid:
- no existing required request field changed;
- occurredAt is optional;
- existing response fields remain;
- canonicalActivityId is additive.

Bridge behavior:
- only authenticated Clerk-owned saves are canonicalized;
- canonical source identity is:
  (Clerk owner, "tracked_hill_session", legacy activityId);
- canonical and legacy writes occur in one database transaction;
- repeated and concurrent identical submissions deduplicate;
- materially changed payloads return HTTP 409;
- a cross-owner collision in the legacy globally unique activity_id returns
  HTTP 409 without leaking the existing row;
- canonicalActivityId links the legacy row to the canonical activity;
- rawGpsTrack and elevationProfile are copied to private evidence rows;
- hill, route, training plan, and training session references become typed
  links;
- route catalogue rows remain separate records;
- no Elevation Bank projection or double-credit behavior was added.

Disable path:
- set CANONICAL_ACTIVITY_BRIDGE_ENABLED=false;
- released legacy tracked-hill writes continue without canonical ingestion;
- no schema rollback is required to disable runtime bridging.


5. IDEMPOTENCY AND CONFLICT POLICY

Canonical unique identity:
- owner_user_id;
- source_type;
- source_id.

Payload comparison:
- relevant canonical summary, source snapshot, links, and evidence are
  normalized deterministically;
- a SHA-256 hash is stored;
- JSON object key order does not alter the hash;
- identical payloads deduplicate;
- materially different payloads create a conflict audit row;
- first accepted canonical values are retained;
- no silent correction/overwrite exists in Phase 1.

10. KNOWN LIMITATIONS AND RISKS

- The existing tracked_hill_sessions.activity_id global unique index remains.
  This preserves current released-client/database behavior but means the legacy
  endpoint must report a cross-owner collision rather than store both legacy
  rows. The canonical table itself correctly stores owner-scoped identities.

- No production legacy records were backfilled. Existing rows receive a
  canonical link only when an authenticated identical save safely passes
  through the compatibility bridge.

- No fuzzy/probable legacy merge engine was implemented. Ambiguous records stay
  separate until a later approved reconciliation policy.

- No correction API exists. Conflicting retries are audited and rejected.

- Qualification rows provide the future foundation only. Phase 1 does not
  evaluate Elevation Bank, Readiness, real summits, Crowns, leaderboards, or
  achievements.

- Raw evidence is private and omitted from activity reads, but no administrator
  evidence-review API or retention scheduler exists in Phase 1.

- Evidence is currently stored as JSONB. Large-track object-storage migration,
  size limits, redaction, and retention policy require a separately approved
  phase.

- Existing tracked_hill_sessions still contains its historical raw_gps_track
  JSONB column for released-client compatibility. Phase 1 does not destructively
  move or erase legacy data.
